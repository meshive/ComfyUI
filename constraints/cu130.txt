# ComfyUI cu130 이미지의 pip 잠금 파일. 한 줄 = `pip freeze --all` 의 한 줄.
#
# 왜 잠그나: custom node 코드는 custom_nodes.txt 의 SHA 로 고정돼 있지만, 각 노드 requirements 와
# 기반 패키지는 빌드 시점에 해석된다. 같은 커밋을 몇 주 뒤 다시 빌드하면 다른 패키지가 들어간다 —
# 라이브 cu128 이미지 2026-08-08 빌드 → 2026-09-23 빌드 실측: onnxruntime 1.28.0→1.30.0,
# pillow 12.2.0→12.3.0, tensorrt 11.2.1.2→11.3.0.99, 패키지 277→281개. 회귀가 나도 어느 패키지
# 때문인지 좁힐 수 없다.
#
# 무엇이 들어 있나: meshive/comfyui:base-torch2.11.0-cu130-rc0928a
# (sha256:2091783dca05aecb55470946ea58420ad0221eb22d33875d3a177434ae484a0f, ComfyUI main 3132359 빌드,
# dev GPU E2E 통과) 의 `pip freeze --all` 에서 torch/torchvision/torchaudio 만 뺀 것이다. 그 셋은
# 빌드가 만드는 /pytorch-constraints.txt 가 맡는다.
# 단, rc0928a 에 있던 고아 3개(httpx2·httpcore2·truststore)는 뺐다. 그 빌드의 기반 패키지 단계가 그날 최신
# huggingface_hub 2.0.0(2026-09-24 출시, httpx2 요구)을 깔았다가, transformers 5.17.0 의 `huggingface-hub<2.0`
# 때문에 1.33.0 으로 내려가며 남은 것이다. 아무것도 요구·import 하지 않는다 (2026-09-29 실측). 잠금으로
# 빌드하면 처음부터 1.33.0 이 깔려 생기지 않는다 — 이 잠금이 막으려는 드리프트의 실제 사례다.
#
# 2026-10-02 ComfyUI v0.37.4 → v0.38.2: 아래 "다시 만드는 법" 1)~2) 의 잠금 없는 빌드를 건너뛰고 6줄만
# 손으로 고쳤다 — v0.38.2 requirements 의 `==` 고정(frontend 1.53.6·workflow-templates 0.11.74·
# comfy-kitchen 0.2.36)과, workflow-templates 0.11.74 가 `==` 로 요구하는 하위 패키지 3개(core 0.3.365·
# json 0.1.100·media-assets-02 0.1.8, PyPI 메타데이터 기준)다. 새 의존성은 없다(comfy-kitchen 은 요구 목록
# 동일, frontend 는 의존성 없음). 같은 커밋에 넣은 ComfyUI-MeshiveInjection 도 의존성이 없다. 손으로 고친
# 것이 맞는지는 빌드 마지막 대조가 확인한다. → 이 잠금으로 빌드한 base-torch2.11.0-cu130-rc1002a
# (amd64 sha256:a7193bff8e452ad6efb6d8c26e97e644d6300643c11882f5b963f8ab51254066)가 대조 283줄 통과,
# dev RTX 5090 에서 기본 워크플로(Z-Image Turbo) 생성 통과 (2026-10-02).
#
# Dockerfile 이 쓰는 방식:
#   - `@` 가 있는 줄(직접 URL)과 주석을 뺀 나머지를 /pip-constraints.txt 로 만들어 PIP_CONSTRAINT 로
#     넘긴다. 직접 URL 을 constraint 로 주면, 요구하는 쪽 URL 모양이 다를 때 pip 가 ResolutionImpossible
#     로 죽는다 (Impact-Pack 의 `git+https://github.com/facebookresearch/sam2` 가 그 경우다).
#   - 빌드 마지막 검사 단계가 설치된 목록 전체를 이 파일과 **정확히** 대조한다. 직접 URL 줄(SAM-2
#     커밋)도 여기서 잡힌다 — 다만 감지일 뿐 고정은 아니다. Impact-Pack 이 커밋 없는 URL 을 요구하므로
#     pip 는 빌드마다 upstream 최신 커밋을 받고, upstream 이 움직이면 대조가 실패해 이 파일을 다시 만들어야
#     한다 (facebookresearch/sam2 는 2b90b9f5 이후 거의 움직이지 않는다).
#   - 기반 패키지 RUN 은 이 파일이 아니라 constraints/cu130-base.txt 를 쓴다 (torch 레이어 캐시 보존 —
#     Dockerfile 의 PIP_BASE_LOCK_FILE 주석). 그 파일의 줄은 모두 여기 같은 버전으로 있어야 한다.
#   - 빌드 때만 적용된다 (ENV 가 아니다). pod 안에서 유저가 하는 pip 설치에는 영향이 없다.
#
# 다시 만드는 법 — ComfyUI·custom node SHA·torch 를 올리면 대개 필요하다 (ComfyUI requirements 의 `==` 고정이나
# 새 의존성 때문에 pip 해석이 먼저 실패하거나, 마지막 대조가 실패한다):
#   1) 잠금 없이, **반드시 임시 태그로** 빌드한다 (EXTRA_TAG 없이 --push 하면 라이브 태그를 덮는다):
#        EXTRA_TAG=-rcMMDDx docker buildx bake base-13-0 --load \
#          --set base-13-0.args.PIP_LOCK_FILE=constraints/none.txt \
#          --set base-13-0.args.PIP_BASE_LOCK_FILE=constraints/none.txt
#   2) 그 이미지의 목록을 후보 잠금으로 이 헤더 아래 본문에 넣는다:
#        docker run --rm --entrypoint pip <이미지> freeze --all | grep -v -E '^(torch|torchvision|torchaudio)=='
#      기반 잠금(constraints/cu130-base.txt)도 그 파일 헤더의 방법으로 다시 만든다.
#   3) 잠금을 켠 채 같은 임시 태그로 다시 빌드한다. 마지막 대조에서 `<` 로만 나오는 줄(잠금에는 있는데 안
#      깔린 것)은, 잠금 없는 빌드의 앞 단계가 깔았다가 뒤 단계가 버전을 바꾸며 남긴 고아다 (위 httpx2 사례).
#      `pip show` 의 Required-by 가 비어 있고 import 하는 곳이 없는지 확인한 뒤 뺀다. `>` 줄이 나오면 잠금이
#      틀린 것이니 원인부터 본다.
#   4) 대조를 통과한 **잠금 빌드**를 GPU E2E 로 검증하고 그 이미지를 승격한다 — 1) 의 잠금 없는 빌드가 아니라
#      이것이 배포되는 바이트다. 위 "무엇이 들어 있나" 의 기준 이미지도 고친다.
#
